# Praxis-RAG 文档分布式锁实施计划

给 DeepSeek v4.1：请在当前仓库按以下计划实施，遵守根目录 AGENTS.md，完成代码、迁移（如需要）、中文部署文档和定向测试。本文是实施计划，描述的是目标设计。

## 一、改动边界

让 Redis 负责文档变更操作的跨实例互斥和续租。MySQL 继续负责任务领取、幂等记录、操作日志、接管时的持有者交接和最终提交校验。这样可以迁出长任务对文档资源租约的周期性 SQL 续租，同时保证暂停后恢复的旧 worker 无法发布或清理新版本。本次不扩展到限流、搜索缓存或 Kafka 消息去重。

请先区分两套现有机制：

| 机制 | 代码入口 | 本次处理 |
| --- | --- | --- |
| 入库任务领取、任务心跳、重试和终态 | `internal/state/document_jobs.go` 的 `Claim` 及配套方法 | 保留。重复收到同一 Kafka 通知仍由 MySQL 原子领取，不再加一层任务 ID 锁 |
| 上传、覆盖、删除、恢复、清理等操作的文档或知识库资源互斥 | `internal/state/uploads.go` 的 `Begin`、`AcquireLock`、`WithLock`、`ClaimRecovery`、`owned` 和 `AssertLockTx` | 将长时互斥迁至 Redis，提交和破坏性写入仍需通过 MySQL 持有者校验 |

## 二、先确定真实锁范围

1. 沿 REST、MCP、document worker、恢复程序和维护 CLI 的调用链，列出每个写入口使用的资源、拿锁时点、释放时点和失败语义。核对实际解析、向量写入与拿锁的先后顺序，只对受锁保护的工作承诺互斥。
2. 从 `UploadJournal.Begin`、`resources`、`acquire` 和 `guardName` 提取冲突矩阵。至少覆盖同一文档、同名上传、同一知识库内不同文档、知识库独占操作。保留同名幂等重放和原有冲突响应。区分事务内短时保护和跨整个操作的长时租约，短时 SQL 唯一性或行锁按需保留。
3. 核对 `internal/state/upload_coordinator.go` 的恢复扫描、版本定向补偿和清理，以及管理端租约展示的读取路径。迁移后它们必须能辨认当前持有者、过期状态和可接管操作。

## 三、实现 Redis 锁和 MySQL 交接

1. **Redis 锁。** 复用现有 Redis 客户端配置和连接能力，为运行时锁使用独立键空间和锁 TTL。沿用现有租约时长和心跳策略时先核对其默认值。每次获取生成唯一 owner token。获取涉及多个资源时原子判断冲突并一次性取得全部资源；原子续期和释放均须核对 owner。知识库独占申请要能发现仍存活的文档锁，反向申请也要互斥。不同文档保留并行能力。如果用资源索引，处理持有者崩溃后的过期条目。多键脚本的相关键放在同一 Redis Cluster slot。
2. **MySQL 交接。** 在开始副作用之前，在短事务里为实际冲突资源登记本次持有者，并使被接替者失效。优先复用现有 owner、操作状态和版本字段。若需增加 fencing epoch（接管代次），由 MySQL 持久化，覆盖同一资源下不同 operation ID 的竞争。明确资源交接和命名空间独占的串行化点。实现前画出“拿到 Redis 锁后暂停，后来者已接管，原请求才到达 MySQL”的时序；协议必须拒绝迟到登记，可采用获取 Redis 锁前读取资源代次、拿锁后在短事务中按预期代次比较并更新，冲突则释放自己的锁并重新走获取流程。单靠拿锁后无条件递增代次，会让旧请求重新成为持有者。
3. **发布与副作用。** 在更新 `document_heads`、写对象、删除、回滚等受保护的 SQL 事务中校验当前持有者。Redis 网络请求放在 SQL 事务外。沿用 Qdrant 和工作目录现有的按操作或版本隔离机制，检查迟到写入、回滚和清理均不能影响接手者的版本。续租失去所有权或无法确认时停止启动新步骤，向可取消的在途调用传递取消信号；对已经发生但结果未知的外部副作用沿用 journal 恢复流程。释放锁只使用本次的 token。
4. **部分失败。** 分别处理 Redis 已拿锁但 MySQL 登记失败、MySQL 登记后进程崩溃、MySQL 已提交但释放锁失败、以及 Redis 重启丢失锁。提交成功后释放失败不得重新执行已提交操作。锁竞争、Redis 不可用、任务已失去所有权要能区分；按现有任务重试契约处理，明确故障发生在 Claim 前后对 attempts 的影响。恢复扫描不能仅凭旧 MySQL 心跳字段接管仍在运行的上传。

## 四、配置、部署与切换

- 明确展示缓存开关和文档锁启用条件。文档锁启用后，所有参与文档写入、恢复或清理的进程必须使用同一套锁配置。缓存 TTL 和锁 TTL 分开；禁用展示缓存时仍应能使用锁。按现有命名习惯补齐必要配置、Compose、启动脚本和就绪检查。
- Redis 临时不可用时，需要新锁的写操作等待重试或返回可重试错误，禁止某个实例自行回退到 MySQL 锁。保持已受理任务可查；区分上传受理、实际处理与同步写操作。展示读取仍可回源 MySQL。
- 核对管理端租约展示、CDC 和 `document_leases` 的现有消费者，保证展示持有者和过期时间有真实来源，保留现有权限及响应契约，不暴露 owner token。不要为了维持展示而恢复每次心跳写 MySQL。
- 采用协调切换：先暂停新文档写入、worker 和恢复入口，排空或明确接管在途操作，再统一切换所有相关进程后恢复入口。回退也须先停写并处理在途操作，防止新旧实例分别拿两种锁。保留已有操作日志和已发布版本；如变更 schema，提供迁移及升级步骤。至少更新 README 或 docs/USAGE.md，并同步受影响的部署说明。

## 五、验收

| 定向用例 | 必须证明的结果 |
| --- | --- |
| 两个 worker 收到同一任务通知 | 现有 MySQL Claim 语义保持，同一轮任务只有一个有效领取者 |
| 两个独立客户端并发覆盖同一文档、同名上传、不同文档并行、知识库独占 | 冲突矩阵和幂等行为与迁移前一致，多资源竞争失败不残留部分锁 |
| A 失去 Redis 锁，B 接手，A 随后续期、释放或提交 | A 不能更改 B 的锁，不能发布，也不能删除 B 的对象或索引 |
| A 拿锁后停在 MySQL 登记之前，B 已完成登记或发布，再恢复 A | A 的迟到登记被拒绝；覆盖同一文档、不同 operation ID 的情况 |
| Redis 故障、重启丢锁、进程在交接点崩溃 | 所有权不确定时停止新步骤；恢复后可继续处理，既有终态和已发布版本正确 |
| 已发布后释放失败、历史未完成操作恢复、管理端租约展示 | 不重复发布；按既有日志恢复或补偿；展示状态与实际锁一致 |

优先扩展现有 state、redisstate、document worker 或 ingest 的相关测试。使用受控暂停或同步点构造关键竞争，避免靠 sleep 碰时序。Redis 原子脚本和过期语义至少用两个独立客户端对真实 Redis 做一次定向集成验证。涉及 MySQL 的用例按仓库要求使用库名含 test 的一次性数据库，执行 go test -p 1 -count=1 -timeout 25m，仅运行改动对应的包或用例。交付时列出实际执行的测试、未验证项、配置变化、升级与回退步骤。
