## 三、共性根因（跨模块）

1. **"耐久字段"只写不读**：`document_jobs.retry_at` 与 `search_tasks.retry_at` 都被写入，但对应的 Claim 从不读取，真正生效的是 Kafka 消费者"5 次 / 约 1.5s"的进程内重试，导致瞬时故障固化为终态（J-01、S-06；J-05 叠加）。
2. **跨存储两步提交缺补偿/幂等**：Redis 快照与 MySQL 状态（S-01）、grants 与邀请状态（H-08）、KB 配置更新与进程内 tenant 缓存（H-02）、Qdrant 与 MySQL 的发布（U-02/U-04）都采用"先 A 后 B、失败不回滚"，且多数没有幂等/对账。
3. **"先查后写"没有共同事务或行锁**：管理员数量保护（R-04）、KB 创建/删除/purge 与发布（H-01）、邀请状态 CAS（H-08）、发布版本栅栏（R-03）都是跨语句 check-then-act，默认 REPEATABLE READ 的普通快照读无法阻止并发提交。
4. **锁顺序与租约语义不统一**：`touch` 只保证单次调用内 cache key 有序，不约束业务行与 revision 行（R-02）；租约时间一半用进程本地钟、一半用 DB 钟（J-04）；Sweep 的回收 UPDATE 缺少租约谓词（J-02）；上传发布又被 namespace guard 串行化（U-02）。
5. **超时与失败分类缺失**：DSN/连接池/HTTP Server 无读写超时（G-01），全仓无 MySQL 死锁/锁超时分类与重试（G-07），破坏性操作无幂等键（H-03/H-06）。

## 四、复核修正与"已核对无缺陷"（避免误报）

**剔除的误报（2 条）**

- 原 C-06「`UploadJournal.Begin/ClaimRecovery` 只 flush 不 touch」：不成立。`Begin`/`ClaimRecovery` 都会调用 `acquire()`，而 `acquire` 通过 `touchCache(..., leases=true)` 在同一事务内 touch 了 `upload_status`/`upload_list`/`leases`（`internal/state/uploads.go:230-256`、`629-660`），随后才 flush。`uploads.go:550` 单独看会误判。
- 原 C-01「nil 写成同 revision 墓碑无法回填」：其触发前提（写入但不 bump revision）不成立；所有活跃写路径都会 touch 对应 key。该机制作为未来新增写路径的**约定风险**保留在 K-04 备注中，不计入统计。

**已核对未发现缺陷的关键设计（负面结论）**

- `document_jobs` + `document_job_outbox` 确为单事务提交（`insertJob` 两条 INSERT + 一次 Commit），并发同 key 由 namespace guard 行锁串行化，唯一键冲突后的回查是自洽兜底。
- Qdrant 可见性顺序正确：向量先以 `upload_version` 暂存，检索过滤器由 `documents/document_heads` 派生的 activeVersions 决定，提交前新版本不可见、提交后已暂存，不存在"读者先看到向量后看到 documents"的错误顺序（但 H-11 的实时查库与 fail-open 是另一问题）。
- 同一文档的并发发布互斥：`Begin` 的"未完成操作"检查在 guard 内执行，文档/名称租约挡住第二个发布者；`ClaimRecovery` 在 guard + operation/lease FOR UPDATE 下复核活租约，未发现两个恢复者同时接管。
- 提交结果不确定的补偿路径：`failDocumentOperation` 先 `journal.Get`，看到 COMMITTED 即按成功返回、不删向量；`Rollback/Compensate` 只接受 active 状态，不会误删已发布版本。
- 缓存快照与 revision 的读视图时序安全：`snapshot` 的 INSERT..ON DUPLICATE / SELECT..FOR UPDATE 都是 current read，loader 的第一条普通 SELECT 才建立一致性读视图，此时已持有 revision 闩锁；写者"业务写+touch"同事务，不会出现 revision 已 bump 而业务未提交。
- Redis 缓存 `Put` 是 WATCH/MULTI 的 revision CAS，旧快照不会覆盖新值；结果快照/artifact 的读取均有 SQL 谓词或 envelope 过期二次校验，未发现越界读取。
- 维护 recovery 未发现偷取活跃租约的破坏性竞态（负面结论，见 H-10）。

## 五、建议优先处理顺序（Top 10）

1. **J-01**（及同类 S-06）：Claim 读取 `retry_at`，把 durable 退避与 consumer 重试解耦，`MaxAttempts` 只用于不可恢复错误。
2. **J-02**：Sweep 的回收 UPDATE 增加 `status/lease_until/owner` 谓词并使用 `SELECT ... FOR UPDATE`（或 SKIP LOCKED）。
3. **S-01**：`Complete` 改为"快照已存在即复用"的幂等语义，并校验 UPDATE RowsAffected；失败时明确返回可重试/冲突。
4. **S-02**：`Attach` 仅在 `client.Enabled()` 时注入 Transient；或启动时对"Kafka 异步搜索 + 无 Redis"显式 fail-fast。
5. **Q-01**：DLQ 对"不可解码"类不可恢复消息显式 ack/转 quarantine，只对"暂时写不进去"保留重试。
6. **H-01/H-04**：purge/删除/创建 KB 统一取 `namespace:exclusive` 租约；publish 事务校验 KB 仍存在；KB 删除级联清理 API key 的 namespace 绑定。
7. **H-02**：`Invalidate` 移到 fence 之前（或 fence 失败也强制失效缓存）；tenant 缓存增加版本/TTL。
8. **H-03/H-06**：破坏性接口引入幂等键，提交后错误统一返回"已生效"语义；purge 409 响应带上已删除数量。
9. **R-01**：`UpsertTx` 重试后校验 RowsAffected，或对 `(namespace,document_id)` 使用 `INSERT ... ON DUPLICATE KEY UPDATE`；同时统一两处 casefold（U-06）。
10. **G-01/G-07**：DSN 加 `timeout/readTimeout/writeTimeout`，HTTP Server 加 Read/Write/Idle 超时；引入 1213/1205 可重试分类与有限重试。
